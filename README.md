# TG Triage

[![CI](https://github.com/maki072/TGTriage/actions/workflows/ci.yml/badge.svg)](https://github.com/maki072/TGTriage/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Бот и веб-панель для личного Telegram Business-аккаунта: сервис слушает входящие сообщения, прогоняет
их через LLM и решает, что из этого реальная задача, а что можно проигнорировать. Задачи попадают
в очередь с приоритетом, черновиком ответа и дедлайном; шум просто оседает в журнале.

Go 1.26, без фреймворков, чистая архитектура (`domain → service → repository/delivery`). Единственная
внешняя зависимость — pure-Go SQLite (WAL), поэтому бинарник статический и без CGO.

## Как это работает

Сообщение приходит через Business API, сохраняется в SQLite, и чат ждёт паузу тишины — по умолчанию
20 секунд, но не дольше 120, если пишут без остановки. Накопленная пачка уходит воркеру: тот собирает
контекст (последние сообщения диалога + открытые задачи с этим собеседником) и вызывает LLM — Claude,
Gemini, Groq, Mistral или OpenRouter, по очереди из списка ключей, — требуя строгий JSON: тип сообщения,
уверенность, заголовок, приоритет, дедлайн, стратегия ответа.

Если уверенность модели ниже порога чувствительности (0.75 / 0.55 / 0.35 для низкой/средней/высокой)
или сообщение явно не задача — оно просто попадает в журнал `analyses`, без карточки владельцу. Если
это продолжение уже открытой задачи, модель определяет это сама, и карточка дополняется, а не
дублируется. Однозначный шум («спасибо», «ок», эмодзи-реакция) отсеивается ещё до LLM — эвристический
словарь ловит бесспорные случаи, не тратя вызов модели.

Задачи управляются кнопками прямо под сообщением: ответить черновиком, взять в работу, закрыть,
отложить, пометить как ложное срабатывание. То же самое дублируется в мини-приложении (Telegram Web
App) — задачи, история, настройки.

Задачу можно завести и вручную: перешлите боту сообщение (или сразу несколько) из любого чата — чужое
или своё. Пачка, пришедшая в пределах пары секунд, склеивается и уходит в LLM с отдельным промптом:
решать «задача или шум» модели уже не нужно, она только оформляет заголовок, суть, приоритет и дедлайн
(относительные сроки считаются от даты исходного сообщения). Пауза триажа и порог уверенности на
пересылку не влияют. Исходный чат у такой задачи неизвестен, поэтому ответить из бота нельзя —
кнопки ответа скрыты.

## Провайдеры

Claude и Gemini — через нативные API; Groq, Mistral и OpenRouter — общий OpenAI-совместимый адаптер.
Нюансы бесплатных тарифов — в [`.env.example`](.env.example) (у Groq антифрод блокирует консоль на
VPN/датацентрах, Mistral требует согласия на обучение на ваших сообщениях, OpenRouter приватнее обоих).

Ключи собираются в цепочку: у одного провайдера может быть сколько угодно ключей, провайдеры можно
перемешивать. Каждый вызов LLM идёт по цепочке сверху вниз — если ключ упёрся в квоту, отклонён или
провайдер недоступен из региона, сразу пробуется следующий. Список редактируется в веб-панели
(«⚙️ Настройки → AI-провайдеры»: провайдер, ключ, порядок), модель для каждого провайдера — там же и в
настройках бота; всё применяется без перезапуска. Кнопка «🧪 Проверить» тестирует каждый ключ отдельно.

## Настройка Telegram

1. Бот у [@BotFather](https://t.me/BotFather), включить **Bot Settings → Business Mode**.
2. Узнать свой user id (например, у @userinfobot) — это `OWNER_ID`.
3. В приложении: **Настройки → Telegram Business → Чат-боты** → подключить бота к нужным чатам,
   выдать права «Отвечать на сообщения» и «Читать сообщения». Нужен Telegram Premium.

Бот реагирует только на `OWNER_ID`, остальные апдейты игнорирует.

## Конфигурация

Всё — в [`.env.example`](.env.example) с комментариями. Обязательны `TELEGRAM_BOT_TOKEN` и `OWNER_ID`;
ключи провайдеров можно задать в `.env` (несколько через запятую) или добавить потом в веб-панели.
Значения из `.env` — дефолты; всё, что поменяли в настройках бота или веб-панели, хранится в БД и
применяется сразу, без перезапуска, кнопка «♻️ Сброс к .env» возвращает как было.

## Сборка

```bash
make test        # go test -race
make build-linux # статический bin/tg-triage-linux-amd64
```

Локально: `cp .env.example .env`, заполнить значения, `make run`.

## Деплой на Debian

```bash
sudo ./deploy/install.sh bin/tg-triage-linux-amd64
sudo nano /etc/tg-triage/tg-triage.env
sudo systemctl restart tg-triage
```

Создаёт системного пользователя, каталоги и systemd-юнит с hardening (`ProtectSystem=strict`,
изолированный `/var/lib/tg-triage` и т.д.). Логи: `journalctl -u tg-triage -f`.

Готовые сборки под тег `vX.Y.Z` собирает GitHub Actions — статический бинарник и инсталлятор-архив
лежат в [Releases](../../releases).

## Ограничения

- В Business-чатах Bot API не даёт ставить реакции — «В работу» вместо этого отмечает сообщение
  прочитанным.
- Ссылок на сообщения в личных чатах не существует — карточка ссылается на профиль собеседника и на
  deep-link `tg://openmessage`, который открывают не все клиенты.
- Голосовые, фото и файлы модель видит только как подпись с длительностью/типом — содержимое медиа
  не распознаётся.
- Текст переписки уходит выбранному LLM-провайдеру; история хранится `MESSAGE_RETENTION_DAYS` дней,
  задачи — бессрочно.
- Один инстанс на токен бота: long polling, вебхук снимается при старте.
